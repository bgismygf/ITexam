# 7-5 鎖定：共享鎖、互斥鎖、兩階段鎖定、死結 🎯

> 本課只有觀念，沒有練習檔。

## 可序列化（Serializability）🎯

**排程（Schedule）**：多個交易的操作交錯執行的順序。

- **序列排程（Serial Schedule）**：一個交易做完，才做下一個。一定正確，但沒有並行
- **可序列化排程（Serializable Schedule）**：交錯執行，但**結果等同於某一種序列排程**。
  這是並行控制追求的目標：**又快又正確**

### 衝突可序列化（Conflict Serializability）

兩個操作**衝突**的條件（三個都要成立）：
1. 屬於**不同**交易
2. 存取**同一個**資料項
3. **至少一個是寫入**

| | T2 讀 | T2 寫 |
|---|:-:|:-:|
| **T1 讀** | 不衝突 | **衝突** |
| **T1 寫** | **衝突** | **衝突** |

**判斷方法：優先圖（Precedence Graph）**
1. 每個交易是一個節點
2. 若 Ti 的某操作與 Tj 的某操作衝突，且 Ti 的**先**執行，畫一條 Ti → Tj 的箭頭
3. **圖中沒有循環（cycle）→ 衝突可序列化** ✅；有循環 → 不可序列化 ❌

例：
```
排程：R1(A) W2(A) W1(A)
R1(A) 在 W2(A) 之前，衝突 → T1 → T2
W2(A) 在 W1(A) 之前，衝突 → T2 → T1
有循環 T1 → T2 → T1 → 不是衝突可序列化
```

## 鎖定（Locking）🎯

最常見的並行控制方法：存取資料前要先「上鎖」。

### 兩種鎖

| 鎖 | 英文 | 用途 | 別稱 |
|---|---|---|---|
| **共享鎖** | Shared Lock（S-Lock） | **讀取**時使用 | 讀取鎖 |
| **互斥鎖** | Exclusive Lock（X-Lock） | **寫入**時使用 | 寫入鎖、排他鎖 |

### 🎯 相容矩陣（必考）

已經有人持有某種鎖時，其他人能不能再加鎖：

| 已持有 \ 想要申請 | S 共享鎖 | X 互斥鎖 |
|---|:-:|:-:|
| **S 共享鎖** | ✅ 可以 | ❌ 要等 |
| **X 互斥鎖** | ❌ 要等 | ❌ 要等 |

💡 **記法**：
- 大家**一起讀**沒問題（S + S ✅）
- 有人在**寫**，別人不能讀也不能寫（X 跟任何鎖都不相容）
- 有人在**讀**，別人不能寫（S + X ❌）

### 鎖定的粒度（Granularity）

| 粒度 | 並行程度 | 管理成本 |
|---|---|---|
| 資料庫 | 最低 | 最低 |
| 資料表 | ↓ | ↓ |
| 頁（Page） | ↓ | ↓ |
| 列（Row） | 最高 | 最高 |

粒度越**小**，越多人可以同時工作（並行度高），但要管理的鎖越多（成本高）。

## 🎯 兩階段鎖定（Two-Phase Locking, 2PL）

只是「有上鎖」還不夠，還需要規定**什麼時候可以解鎖**。

### 規則：每個交易分成兩個階段

```
鎖的數量
  ▲
  │        ╱‾‾‾‾╲
  │      ╱       ╲
  │    ╱           ╲
  │  ╱               ╲
  └──────────────────────▶ 時間
    成長階段    │  縮減階段
   (Growing)  鎖點  (Shrinking)
   只能加鎖         只能解鎖
   不能解鎖         不能加鎖
```

1. **成長階段（Growing Phase）**：只能**取得**鎖，不能釋放
2. **縮減階段（Shrinking Phase）**：只能**釋放**鎖，不能再取得

**一旦開始解鎖，就不能再加任何鎖。**

### 🎯 2PL 的重要性質

| 性質 | 2PL |
|---|---|
| 保證**衝突可序列化** | ✅ **是** |
| 防止**死結** | ❌ **不能**（2PL 仍可能發生死結） |
| 防止**連鎖回復** | ❌ 基本 2PL 不能 |

### 2PL 的變形

| 種類 | 規則 | 優點 |
|---|---|---|
| **嚴格 2PL**（Strict 2PL） | **互斥鎖**要到交易 COMMIT / ROLLBACK 後才釋放 | 避免**連鎖回復**（Cascading Rollback） |
| **嚴謹 2PL**（Rigorous 2PL） | **所有鎖**都到交易結束才釋放 | 更簡單，大部分商用資料庫採用 |
| **保守 2PL**（Conservative 2PL） | 交易開始前**一次取得所有需要的鎖** | **可以避免死結**，但很難事先知道需要哪些鎖 |

**連鎖回復**：T1 回復，導致讀過 T1 未提交資料的 T2 也要回復，T2 又導致 T3 回復……

## 🎯 死結（Deadlock）

**兩個以上的交易互相等待對方釋放鎖，結果誰都無法繼續。**

| 時間 | T1 | T2 |
|---|---|---|
| t1 | 鎖定 A（X-Lock） | |
| t2 | | 鎖定 B（X-Lock） |
| t3 | 想鎖定 B → **等 T2** | |
| t4 | | 想鎖定 A → **等 T1** |
| | 💀 互相等待，永遠卡住 | |

### 發生死結的四個必要條件（作業系統也會考）

1. **互斥（Mutual Exclusion）**：資源一次只能給一個人用
2. **持有並等待（Hold and Wait）**：拿著一個資源，同時等另一個
3. **不可搶奪（No Preemption）**：不能強行搶走別人的資源
4. **循環等待（Circular Wait）**：T1 等 T2、T2 等 T1，形成循環

**四個條件同時成立**才會發生死結，破壞任何一個就能預防。

### 處理死結的方法

| 方法 | 說明 |
|---|---|
| **預防**（Prevention） | 事先避免四個條件之一。例如保守 2PL、依固定順序加鎖 |
| **避免**（Avoidance） | 依時間戳記決定等待或回復：<br>• **Wait-Die**：老的等年輕的；年輕的要等老的時，**自己回復**<br>• **Wound-Wait**：老的要等年輕的時，**讓年輕的回復**；年輕的等老的 |
| **偵測與復原**（Detection） | 定期畫**等待圖（Wait-for Graph）**，**有循環就是死結**，選一個交易（犧牲者）回復 |
| **逾時**（Timeout） | 等太久就自動回復 |

💼 實務上，大部分資料庫採用**偵測**：發現死結時，自動選一個交易回復，並回傳錯誤，
程式要能處理這個錯誤並**重試**。

💼 **避免死結的寫程式技巧**：所有交易都**用相同的順序**存取資源（例如都先鎖帳戶 A 再鎖 B）。

## 其他並行控制方法（了解即可）

| 方法 | 說明 |
|---|---|
| **時間戳記排序**（Timestamp Ordering） | 每個交易有時間戳記，依時間順序決定誰先，衝突時回復較晚的交易。**不會死結** |
| **樂觀並行控制**（Optimistic） | 先做再說，提交時才檢查有沒有衝突。適合衝突少的情況 |
| **多版本並行控制**（MVCC） | 保留資料的多個版本，讀取不會擋寫入。PostgreSQL、Oracle、MySQL InnoDB 都使用 |

## 小測驗

1. 某資料項已被交易 T1 加上共享鎖，交易 T2 要求對該資料項加互斥鎖，結果為？
   (A) 立即獲得 (B) 必須等待 (C) T1 被迫回復 (D) 兩者同時持有

2. 關於兩階段鎖定協定（2PL），下列敘述何者正確？
   (A) 可以防止死結
   (B) 可以保證衝突可序列化
   (C) 交易可以在任何時候加鎖和解鎖
   (D) 縮減階段可以再取得新的鎖

3. 在等待圖（Wait-for Graph）中，出現什麼情況代表發生死結？
   (A) 有孤立節點 (B) 有循環 (C) 節點數大於 2 (D) 有雙向箭頭以外的邊

4. 下列何者「不是」死結發生的必要條件？
   (A) 互斥 (B) 持有並等待 (C) 可搶奪 (D) 循環等待
