# 7-6 復原機制：Log、Checkpoint 🎯

> 本課只有觀念，沒有練習檔。

## 觀念

資料庫可能遇到各種故障，**復原（Recovery）** 機制負責在故障後把資料庫恢復到正確的狀態，
確保交易的**原子性（A）** 和**持久性（D）**。

## 故障的種類

| 種類 | 例子 | 記憶體資料 | 硬碟資料 | 復原方式 |
|---|---|---|---|---|
| **交易故障** | 違反限制、除以 0、死結被選為犧牲者 | 保留 | 保留 | 回復該交易（Undo） |
| **系統故障** | 停電、作業系統當機 | **遺失** | 保留 | 用 Log 做 Undo + Redo |
| **媒體故障** | 硬碟損壞 | 遺失 | **遺失** | 從**備份**還原，再用 Log 重做 |

## 🎯 日誌（Log）

**Log** 是一個檔案，記錄資料庫的每一個修改動作：

```
<T1, start>
<T1, A, 1000, 900>     ← 交易 T1 把資料 A 從 1000（舊值）改成 900（新值）
<T1, B, 2000, 2100>
<T1, commit>
```

每筆記錄包含：交易編號、資料項、**舊值**（用來 Undo）、**新值**（用來 Redo）。

### 🎯 WAL 規則（Write-Ahead Logging，先寫日誌）

**修改資料庫之前，一定要先把 Log 寫入硬碟。**

為什麼？如果先改資料、還沒寫 Log 就當機，就不知道剛剛改了什麼，無法復原。

## 🎯 Undo 與 Redo

| 操作 | 意思 | 用在什麼交易 | 使用 Log 中的 | 確保 |
|---|---|---|---|---|
| **Undo**（復原） | 把修改**還原**成舊值 | 當機時**還沒 COMMIT** 的交易 | **舊值** | **原子性** |
| **Redo**（重做） | 把修改**重新**做一次 | 當機前**已經 COMMIT** 的交易 | **新值** | **持久性** |

為什麼已經 COMMIT 的交易還要 Redo？因為為了效能，資料庫 COMMIT 時通常只保證 **Log**
寫入硬碟，**資料本身可能還在記憶體的緩衝區**，當機時就遺失了。

## 🎯 兩種更新策略

| 策略 | 做法 | 需要 Undo | 需要 Redo |
|---|---|:-:|:-:|
| **延遲更新**（Deferred Update） | COMMIT **之後**才真正寫入資料庫 | ❌ 不需要（沒 COMMIT 的根本沒寫進去） | ✅ 需要 |
| **立即更新**（Immediate Update） | 交易執行**過程中**就寫入資料庫 | ✅ 需要 | ✅ 需要 |

## 🎯 檢查點（Checkpoint）

**問題**：當機後，難道要從 Log 的第一筆開始檢查嗎？Log 可能有好幾個月的資料。

**解法**：定期建立**檢查點**：
1. 把記憶體中所有修改過的資料寫入硬碟
2. 在 Log 寫入一筆 `<checkpoint>` 記錄

**檢查點之前已經 COMMIT 的交易，資料一定已經在硬碟上了，復原時不用理它。**

### 🎯 經典考題：依檢查點判斷各交易要做什麼

```
時間 ──────────────────┬───────────────────────┬──────▶
                   檢查點 tc                  當機 tf
T1  ├────────┤ commit                                       → 不用處理
T2      ├──────────────────────┤ commit                     → Redo
T3              ├──────────────────────────────────────── ✗ → Undo
T4                          ├──────────┤ commit             → Redo
T5                                    ├──────────────── ✗  → Undo
```

| 交易 | 狀況 | 處理 |
|---|---|---|
| T1 | 檢查點**之前**就 COMMIT | **不用處理**（已經寫入硬碟） |
| T2 | 檢查點之前開始，檢查點**之後、當機之前** COMMIT | **Redo** |
| T3 | 檢查點之前開始，當機時**還沒 COMMIT** | **Undo** |
| T4 | 檢查點之後開始，當機之前 COMMIT | **Redo** |
| T5 | 檢查點之後開始，當機時**還沒 COMMIT** | **Undo** |

💡 **判斷口訣**：
- **當機前有 COMMIT** → **Redo**（除非在檢查點前就 COMMIT → 不用管）
- **當機前沒 COMMIT** → **Undo**

## 其他復原技術（了解即可）

| 技術 | 說明 |
|---|---|
| **影子分頁**（Shadow Paging） | 修改時不覆蓋原頁，而是寫到新的頁；COMMIT 時切換到新頁。不需要 Log 做 Undo |
| **ARIES** | 業界標準的復原演算法：分析（Analysis）→ 重做（Redo）→ 復原（Undo）三階段 |

## 💼 備份策略

| 備份類型 | 內容 | 還原時需要 |
|---|---|---|
| **完整備份**（Full） | 整個資料庫 | 最近一次完整備份 |
| **差異備份**（Differential） | 上次**完整**備份後變動的部分 | 完整 + 最近一次差異 |
| **增量備份**（Incremental） | 上次**任何**備份後變動的部分 | 完整 + 之後**所有**增量 |
| **交易日誌備份** | Log | 可以還原到任何時間點 |
