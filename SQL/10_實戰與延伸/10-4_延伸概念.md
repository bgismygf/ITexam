# 10-4 延伸概念：NoSQL、資料倉儲、OLTP 與 OLAP、分散式資料庫 🎯

> 本課只有觀念，沒有練習檔。考試偶爾出現，工作上也要有基本認識。

## 🎯 OLTP vs OLAP

| | OLTP（線上交易處理） | OLAP（線上分析處理） |
|---|---|---|
| 英文 | Online **Transaction** Processing | Online **Analytical** Processing |
| 用途 | 日常營運：下單、轉帳、刷卡、繳費 | 分析決策：報表、趨勢、預測 |
| 操作 | 大量的**小交易**（新增、修改少量資料） | 少量的**大查詢**（讀取、彙總大量資料） |
| 資料 | **目前**的資料 | **歷史**資料（好幾年） |
| 設計 | **正規化**（3NF），減少重複 | **反正規化**（星狀綱要），加快查詢 |
| 使用者 | 一般使用者、應用程式 | 分析師、主管 |
| 例子 | 台電的繳費系統 | 台電分析各區十年來的用電趨勢 |

## 🎯 資料倉儲（Data Warehouse）

**把各個 OLTP 系統的資料整合起來，專門用來分析的資料庫。**

Bill Inmon 的定義，資料倉儲的四個特性：

| 特性 | 意思 |
|---|---|
| **主題導向**（Subject-oriented） | 依分析主題（客戶、產品、銷售）組織，而不是依應用程式 |
| **整合性**（Integrated） | 整合多個來源，統一格式（例如性別有的系統用 M/F、有的用 1/0，要統一） |
| **時間變異**（Time-variant） | 保存歷史資料，可以做時間趨勢分析 |
| **非揮發性**（Non-volatile） | 資料載入後**不會修改或刪除**，只會新增 |

### ETL

資料從 OLTP 系統進入資料倉儲的過程（10-2 課做過小規模的）：
**Extract（擷取）→ Transform（轉換）→ Load（載入）**

### 🎯 星狀綱要（Star Schema）

資料倉儲最常見的設計：

```
                ┌────────────┐
                │ 日期維度表   │
                │ (年/季/月/日) │
                └─────┬──────┘
┌────────────┐  ┌─────┴──────┐  ┌────────────┐
│ 產品維度表   │──│   事實表    │──│ 客戶維度表   │
│(名稱/類別)  │  │(銷售金額/數量)│  │(地區/年齡層) │
└────────────┘  └─────┬──────┘  └────────────┘
                ┌─────┴──────┐
                │ 門市維度表   │
                └────────────┘
```

| 表 | 內容 |
|---|---|
| **事實表**（Fact Table） | 可量測的數值（銷售金額、數量），加上各維度的外來鍵。資料量很大 |
| **維度表**（Dimension Table） | 描述性的資訊（產品名稱、客戶地區、日期的年/季/月）。通常反正規化 |

**雪花綱要（Snowflake Schema）**：把維度表再正規化拆開（例如產品 → 類別 → 大類），像雪花一樣分岔。

### 🎯 OLAP 操作

| 操作 | 意思 | 例子 |
|---|---|---|
| **上捲**（Roll-up） | 往**粗**的層級彙總 | 月 → 季 → 年 |
| **下鑽**（Drill-down） | 往**細**的層級展開 | 年 → 季 → 月 |
| **切片**（Slice） | 固定**一個**維度的值 | 只看 2024 年 |
| **切塊**（Dice） | 固定**多個**維度的範圍 | 2024 年、北部、3C 產品 |
| **旋轉**（Pivot） | 轉換觀看的角度（列、欄互換） | 樞紐分析表 |

### 其他名詞

| 名詞 | 意思 |
|---|---|
| **資料超市**（Data Mart） | 針對**單一部門**的小型資料倉儲 |
| **資料湖**（Data Lake） | 存放**原始**、各種格式（結構化、半結構化、非結構化）的大量資料 |
| **資料探勘**（Data Mining） | 從大量資料中找出隱藏的規律（關聯規則、分類、分群） |
| **商業智慧**（BI） | 用來分析和呈現資料的工具和流程，例如 Power BI、Tableau |

## 🎯 NoSQL

**NoSQL（Not Only SQL）**：非關聯式資料庫的統稱，為了解決關聯式資料庫在**超大規模**、
**結構多變**的資料上遇到的困難。

### 四種類型

| 類型 | 資料模型 | 代表產品 | 適合 |
|---|---|---|---|
| **鍵值型**（Key-Value） | `key → value` | Redis、DynamoDB | 快取、Session、購物車 |
| **文件型**（Document） | JSON 文件 | MongoDB、Firestore | 內容管理、結構多變的資料 |
| **欄族型**（Column-family / Wide-column） | 依欄位族群存放 | Cassandra、HBase | 大量寫入、時間序列、物聯網 |
| **圖形型**（Graph） | 節點與邊 | Neo4j | 社群網路、推薦系統、詐騙偵測 |

文件型範例（MongoDB）：一份文件就包含題目和選項，不用 JOIN
```json
{
  "question_id": 19,
  "year": 112,
  "content": "在輸入欄位中插入惡意 SQL 語法的攻擊稱為？",
  "options": { "A": "XSS", "B": "DDoS", "C": "SQL Injection", "D": "釣魚攻擊" },
  "answer": "C",
  "topics": ["資料庫", "資訊安全"]
}
```

### SQL vs NoSQL

| | 關聯式（SQL） | NoSQL |
|---|---|---|
| 結構 | 固定綱要（Schema），要先定義表 | 彈性綱要（Schema-less） |
| 擴充方式 | **垂直擴充**（Scale-up：買更強的機器） | **水平擴充**（Scale-out：加更多機器） |
| 交易 | **ACID** | 多為 **BASE**（最終一致性） |
| JOIN | 強大 | 通常不支援或很弱 |
| 適合 | 結構明確、重視一致性（金融、訂單） | 海量、結構多變、高併發（社群、物聯網、日誌） |

💼 實務上常**混合使用**：訂單用 MySQL、快取用 Redis、搜尋用 Elasticsearch、日誌用 MongoDB。

## 🎯 分散式資料庫與 CAP 定理

**分散式資料庫**：資料分散存放在多台電腦（節點）上。

### CAP 定理

分散式系統**最多只能同時滿足以下三項中的兩項**：

| 特性 | 意思 |
|---|---|
| **C**onsistency（一致性） | 所有節點在同一時間看到**相同**的資料 |
| **A**vailability（可用性） | 每個請求都能得到回應（不會失敗） |
| **P**artition tolerance（分區容錯） | 節點之間的網路斷線時，系統仍能運作 |

網路斷線（P）在分散式系統中無法避免，所以實際上是在 **C 和 A 之間取捨**：
- **CP**：寧可暫停服務，也要保證資料一致（例如銀行系統、HBase、MongoDB 預設）
- **AP**：寧可資料暫時不一致，也要持續服務（例如 Cassandra、DynamoDB、社群網站）

### 分散式資料庫的技術

| 技術 | 說明 |
|---|---|
| **分片**（Sharding） / 水平分割 | 依某個鍵把資料**分散**到不同節點，例如會員編號 1～100 萬在 A 機、100 萬以上在 B 機 |
| **垂直分割** | 依**欄位**分割，常用的欄位和不常用的分開存放 |
| **複製**（Replication） | 同一份資料存在**多個**節點，提高可用性和讀取效能（主從複製 Master-Slave） |
| **兩階段提交**（2PC, Two-Phase Commit） | 跨多個節點的交易：① 準備階段（大家都說 OK）② 提交階段（一起提交）。確保分散式交易的原子性 |

### 🎯 分散式資料庫的透通性（Transparency）

**透通性**：資料雖然分散在很多地方，使用者卻**感覺不到**，用起來就像一個集中式資料庫。

| 透通性 | 使用者**不需要知道**的事 | 例子 |
|---|---|---|
| **分割透通性**（Fragmentation） | 資料表被**切成幾塊**（水平或垂直分割） | 會員表依地區拆成北、中、南三塊，查詢時照樣寫 `SELECT * FROM 會員` |
| **位置透通性**（Location） | 每一塊資料**放在哪個節點** | 不用寫「去台中機房查」 |
| **複製透通性**（Replication） | 資料**有幾份副本**、存在哪裡 | 更新時 DBMS 自動同步所有副本 |
| **區域對應透通性**（Local Mapping） | 各節點的 DBMS 產品、檔案名稱 | 只知道分割和位置，但不用管各節點用什麼產品 |
| **交易透通性**（Transaction） | 交易跨了幾個節點 | 跨節點的交易一樣滿足 ACID（靠 2PC） |
| **故障透通性**（Failure） | 某個節點故障了 | 系統自動改用其他副本，繼續服務 |
| **異質透通性**（Heterogeneity） | 各節點用**不同的 DBMS** | 台北用 Oracle、高雄用 SQL Server，查詢語法一樣 |

💡 **分割、位置、區域對應**三者是一個由高到低的層次：
- 有**分割透通性** → 使用者連「表被切開」都不知道（最高）
- 只有**位置透通性** → 要指定查哪一塊，但不用知道在哪台機器
- 只有**區域對應透通性** → 要指定哪一塊、在哪個節點，但不用知道當地的檔案名稱
