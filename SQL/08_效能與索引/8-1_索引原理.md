# 8-1 索引原理：B-Tree / B+ Tree、雜湊索引 🎯💼

## 觀念

**索引（Index）** 就像書的**目錄**或**索引頁**：

- 沒有索引：要找「死結」這個詞，只能**從第一頁翻到最後一頁**（全表掃描，Full Table Scan）
- 有索引：翻到書後面的索引頁，找到「死結 → 第 235 頁」，**直接翻過去**

```sql
CREATE INDEX idx_log_question ON practice_log(question_id);
```

之後執行 `WHERE question_id = 8`，資料庫就能用索引快速找到，不用掃過全部資料。

## 索引的代價

| 優點 | 缺點 |
|---|---|
| **查詢**（SELECT、WHERE、JOIN、ORDER BY）變快 | **新增、修改、刪除**變慢（要同時更新索引） |
| | 佔用額外的**儲存空間** |

就像書的索引：書的內容改了，索引頁也要跟著改。

## 🎯 B-Tree（平衡樹）

大部分資料庫的索引都是 **B-Tree** 或 **B+ Tree** 結構。

### B-Tree 的特性

- **平衡（Balanced）**：所有葉節點都在**同一層**，所以任何資料的搜尋時間都差不多
- **多路（Multi-way）**：每個節點可以有**很多個**子節點（不像二元樹只有 2 個），樹就會很「矮」
- **有序**：節點內的鍵值是排序的

```
                    [ 30 | 60 ]
                  /      |      \
        [10 | 20]    [40 | 50]    [70 | 80 | 90]
```

### 🎯 m 階 B-Tree 的規則

| 規則 | 內容 |
|---|---|
| 每個節點最多 | **m** 個子節點、**m − 1** 個鍵 |
| 非根的內部節點最少 | **⌈m/2⌉** 個子節點 |
| 根節點最少 | **2** 個子節點（除非它本身就是葉節點） |
| 葉節點 | 都在**同一層** |
| 有 k 個子節點的節點 | 有 **k − 1** 個鍵 |

為什麼樹要「矮」？因為每往下一層，就要**讀一次硬碟**（很慢）。
一個節點的大小通常等於一個硬碟頁（例如 4KB / 8KB），可以放幾百個鍵，
所以 **3～4 層**的 B-Tree 就可以存放數百萬到上億筆資料。

## 🎯 B+ Tree（資料庫最常用）

B+ Tree 是 B-Tree 的變形，**大部分資料庫實際使用的是 B+ Tree**。

```
                     [ 30 | 60 ]                 ← 內部節點：只存鍵（當路標）
                   /      |      \
    [10 | 20] ⇄ [30 | 40 | 50] ⇄ [60 | 70 | 80]  ← 葉節點：存所有資料，而且串成鏈結串列
```

### 🎯 B-Tree vs B+ Tree（必考）

| | B-Tree | B+ Tree |
|---|---|---|
| 資料存在哪裡 | **所有節點**都可以存資料 | **只有葉節點**存資料，內部節點只存鍵 |
| 葉節點之間 | 不相連 | **用鏈結串列串起來** |
| 鍵是否重複出現 | 每個鍵只出現一次 | 內部節點的鍵會在葉節點**再出現一次** |
| 範圍查詢（BETWEEN、>、<） | 要在樹中來回走 | **很快**：找到起點後，沿著葉節點往後走 |
| 每個節點能放的鍵 | 較少（還要放資料） | **較多**（內部節點只放鍵）→ 樹更矮 |
| 搜尋時間 | 不固定（可能在內部節點就找到） | **固定**（一定要走到葉節點） |

💡 **為什麼資料庫偏好 B+ Tree**：範圍查詢和排序非常常見，葉節點串在一起讓這些操作很快。

## 🎯 雜湊索引（Hash Index）

用**雜湊函數**直接算出資料的位置：

```
hash('S001') → 第 37 號桶子 → 直接找到
```

| | B+ Tree 索引 | 雜湊索引 |
|---|---|---|
| 等值查詢（=） | 快，O(log n) | **最快**，平均 O(1) |
| 範圍查詢（>、<、BETWEEN） | ✅ 快 | ❌ **不支援**（雜湊後順序被打亂） |
| 排序（ORDER BY） | ✅ 可以利用 | ❌ 不行 |
| 前綴查詢（LIKE 'abc%'） | ✅ 可以 | ❌ 不行 |

**碰撞（Collision）**：不同的鍵算出相同的位置，需要額外處理（例如鏈結法、開放定址法）。

💼 實務上，雜湊索引用在「只需要等值查詢」的場合，例如 MySQL 的 MEMORY 引擎、記憶體中的雜湊 JOIN。
**大部分情況用預設的 B+ Tree 就對了。**

## 🎯 其他索引名詞

| 名詞 | 意思 |
|---|---|
| **主索引**（Primary Index） | 建立在**排序鍵（通常是主鍵）**上的索引 |
| **次索引**（Secondary Index） | 建立在其他欄位上的索引 |
| **密集索引**（Dense Index） | **每一筆**資料都有一個索引項目 |
| **稀疏索引**（Sparse Index） | 只有**部分**資料有索引項目（例如每個資料頁一個）。資料必須依索引鍵**排序**才能使用 |
| **唯一索引**（Unique Index） | 索引的值不可重複。建立 PRIMARY KEY 或 UNIQUE 時會自動建立 |
| **複合索引**（Composite Index） | 建立在**多個欄位**上的索引（8-3 課） |
| **點陣圖索引**（Bitmap Index） | 適合**值的種類很少**的欄位（例如性別），常用於資料倉儲 |

## 🎯 計算查詢要存取幾個硬碟頁 📌（113 年資訊管理申論題，10 分）

### 為什麼要算「硬碟頁」

資料庫的資料存在硬碟上，查詢時要先把資料**載入記憶體**才能運算。
硬碟一次讀一整「頁」（Page / Block），而讀硬碟比 CPU 運算慢非常多，
所以**查詢成本 ≈ 要讀幾個硬碟頁**。考題通常只算這個，CPU 時間忽略不計。

### 基本公式

先算出資料總共占幾頁：

```
資料頁數 = ⌈ 總筆數 ÷ 每頁筆數 ⌉
```

再依查詢方式套用：

| 查詢方式 | 要讀幾頁 | 說明 |
|---|---|---|
| **全表掃描**（沒有可用的索引） | 資料頁數 | 每一頁都要讀 |
| **排序檔 + 二分搜尋**（沒有索引，但資料依該欄位排序） | ⌈log₂ 資料頁數⌉ | 每次讀中間那頁，砍掉一半 |
| **B+ Tree 索引，等值查詢唯一鍵**（例如 `WHERE 主鍵 = ...`） | 樹高 + 1 | 從根走到葉節點（樹高頁），再讀 1 個資料頁 |
| **叢集索引，範圍查詢** | 樹高 + ⌈符合筆數 ÷ 每頁筆數⌉ | 找到起點後，資料在硬碟上**連續存放**，一頁一頁往後讀就好 |
| **非叢集索引，範圍查詢** | 樹高 + 葉節點頁數 + **符合筆數** | 資料**分散**在不同頁，最壞情況每一筆都要讀一個不同的資料頁 |

> 💡 「樹高」是指從根到葉節點共有幾層，每一層讀 1 頁。題目寫「含葉節點共 4 層」，樹高就是 4。

### 範例：113 年考題

**題目條件**
- `Product` 資料表共 **100,000 筆**，每一硬碟頁可放 **200 筆**
- `pNo`（主鍵）和 `unitPrice` 各有一個 B+ Tree 索引，**都是 4 層**（含葉節點）
- `unitPrice` 的索引宣告為 `CLUSTER`（**叢集索引**），所以資料在硬碟上是**依 unitPrice 排序**存放的

```sql
CREATE INDEX PriceIndex ON Product(unitPrice) CLUSTER;
```

**先算資料頁數**

```
100,000 ÷ 200 = 500 頁
```

**(1) `SELECT * FROM Product WHERE pNo = 'xxxxxx'`**

- pNo 是主鍵，最多只有 1 筆符合
- 走 pNo 的 B+ Tree：從根到葉，讀 **4 頁**
- 葉節點記錄這筆資料在哪一頁，再讀 **1 個資料頁**

```
4 + 1 = 5 頁
```

**(2) `SELECT * FROM Product WHERE unitPrice > z`（z 為任意整數）**

- z 是任意值，**平均**會有一半的資料符合：100,000 ÷ 2 = 50,000 筆
- 走 unitPrice 的 B+ Tree，找到第一筆 > z 的位置：讀 **4 頁**
- 因為是**叢集索引**，符合的資料在硬碟上**連續存放**，往後依序讀：
  50,000 ÷ 200 = **250 頁**

```
4 + 250 = 254 頁
```

⚠️ 這題沒有公布官方解答，上面是常見的解法。作答時要**寫出假設**，例如「z 為任意值，平均有一半資料符合」，以及每一步的算式，計算過程也是給分重點。
有些解法認為最後一層葉節點就可以直接定位資料頁，會算成 3 + 250 = 253 頁。只要假設寫清楚，通常都能得分。

### 延伸：如果 unitPrice 是「非叢集」索引呢？

資料沒有依 unitPrice 排序，50,000 筆符合的資料**分散**在 500 頁裡：

- 最壞情況，每一筆都要讀一次資料頁：約 **50,000 次**
- 直接全表掃描只要 **500 頁**

👉 **符合的資料太多時，非叢集索引反而比全表掃描慢**，所以資料庫的最佳化器會改用全表掃描。
這也是 8-3 課「何時該建索引」的重要觀念。

| 情況 | 讀取頁數 |
|---|---|
| 全表掃描 | 500 |
| 主鍵等值查詢（B+ Tree 4 層） | 5 |
| unitPrice > z，叢集索引 | 約 254 |
| unitPrice > z，非叢集索引 | 最壞約 50,000（不如全表掃描） |

## 語法

```sql
CREATE INDEX 索引名稱 ON 資料表(欄位);                 -- 一般索引
CREATE UNIQUE INDEX 索引名稱 ON 資料表(欄位);          -- 唯一索引
CREATE INDEX 索引名稱 ON 資料表(欄位1, 欄位2);         -- 複合索引
DROP INDEX 索引名稱;                                   -- 刪除索引
```
