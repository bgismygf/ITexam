# 8-3 何時該建索引、何時反而變慢 💼

## ✅ 適合建索引的欄位

| 情況 | 例子 |
|---|---|
| 常出現在 **WHERE** 條件 | `WHERE email = ?`、`WHERE status = ?` |
| 常用來 **JOIN** 的欄位（**外來鍵**） | `questions.exam_id`、`practice_log.question_id` |
| 常用來 **ORDER BY** / **GROUP BY** | `ORDER BY created_at DESC` |
| **選擇性高**（值的種類多）的欄位 | 身分證字號、email、訂單編號 |

💼 **外來鍵記得建索引**。很多資料庫（包括 SQLite、PostgreSQL）**不會**自動替外來鍵建索引，
但幾乎所有 JOIN 都會用到它。（MySQL InnoDB 會自動建）

## ❌ 不適合建索引的情況

| 情況 | 原因 |
|---|---|
| **資料量很小**的表 | 全部掃一遍比查索引還快 |
| **選擇性低**的欄位 | 例如「性別」只有 2 種值，用索引還是要讀一半的資料，不如直接全表掃描 |
| **頻繁寫入、很少查詢**的表 | 例如日誌表，每次寫入都要更新索引 |
| **很少用來查詢**的欄位 | 白白佔空間、拖慢寫入 |
| 已經被其他索引**涵蓋**的 | 有 (a, b) 的複合索引，通常就不需要單獨的 (a) 索引 |

## 選擇性（Selectivity）

```
選擇性 = 不同值的數量 / 總筆數
```
- 越接近 **1** → 選擇性越高 → 越適合建索引（例如主鍵 = 1）
- 越接近 **0** → 選擇性越低 → 越不適合（例如性別 ≈ 0）

## 🎯 複合索引與最左前綴原則

**複合索引**：建立在多個欄位上的索引。

```sql
CREATE INDEX idx_abc ON t(a, b, c);
```

索引會**先依 a 排序，a 相同再依 b，b 相同再依 c**，就像電話簿先依姓、再依名排序。

### 最左前綴原則（Leftmost Prefix）

查詢條件必須**從最左邊的欄位開始、連續使用**，才能用到索引：

| 查詢條件 | 能用到 (a, b, c) 索引嗎 |
|---|---|
| `WHERE a = 1` | ✅ |
| `WHERE a = 1 AND b = 2` | ✅ |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ |
| `WHERE b = 2` | ❌ 沒有 a |
| `WHERE b = 2 AND c = 3` | ❌ 沒有 a |
| `WHERE a = 1 AND c = 3` | ⚠️ 只用到 a 的部分 |

💡 **類比**：電話簿依「姓 → 名」排序。
- 找「姓王的人」→ 很快 ✅
- 找「名叫小明的人」→ 只能從頭翻到尾 ❌

### 欄位順序怎麼排

1. **等值條件**（=）的欄位放前面，**範圍條件**（>、<、BETWEEN）的放後面
2. 常單獨使用的欄位放前面
3. 選擇性高的欄位放前面（一般原則，但不是絕對）

## 💼 實務流程

1. **不要一開始就到處建索引**
2. 系統上線後，找出**慢的查詢**（大部分資料庫有「慢查詢日誌」功能）
3. 用 **EXPLAIN** 看執行計畫（下一課），確認是不是全表掃描
4. 針對性地建索引，再用 EXPLAIN 確認有用到
5. 定期檢查**沒在用的索引**，刪掉
