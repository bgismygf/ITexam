# 6-7 反正規化 💼

## 觀念

**反正規化（Denormalization）**：**故意**讓資料表不符合高階正規化，
用「一些資料重複」換取「**查詢效能**」或「**簡化查詢**」。

## 為什麼要反正規化

正規化之後，資料分散在很多張表，查詢時要 JOIN 很多次：

```sql
-- 顯示一筆訂單的完整資訊，要 JOIN 4 張表
SELECT ...
FROM orders o
JOIN customers c   ON ...
JOIN order_items i ON ...
JOIN products p    ON ...
```

資料量很大、查詢很頻繁時，JOIN 的成本會很高。

## 正規化 vs 反正規化

| | 正規化 | 反正規化 |
|---|---|---|
| 資料重複 | 少 | 多 |
| 寫入（新增/修改） | 快、簡單 | 慢、要同步更新多處 |
| 查詢 | 要 JOIN，可能較慢 | 少 JOIN，較快 |
| 資料一致性 | 容易維持 | **要自己想辦法維持** |
| 適合 | 寫入頻繁的系統（OLTP） | 讀取為主的系統（報表、分析、OLAP） |

## 💼 常見的反正規化手法

### 1. 冗餘欄位：把常用的欄位複製一份

```sql
-- 訂單表直接存客戶姓名，查訂單時不用 JOIN 客戶表
orders(order_id, customer_id, customer_name, ...)
```

### 2. 彙總欄位：預先算好統計值

```sql
-- 考試表加上「已作答次數」，不用每次都 COUNT
exams(exam_id, ..., practice_count)
```

### 3. 歷史快照：保存「當時」的值（這其實是**必要的**）

訂單明細要存「**購買當時的單價**」，而不是參照商品表的目前價格：
```sql
order_items(order_id, product_id, unit_price, quantity)
--                                ↑ 商品之後漲價，舊訂單的金額不能跟著變
```
這看起來像資料重複，但其實 `unit_price` 和 `products.price` 是**不同的事實**
（成交價 vs 目前售價），所以不算違反正規化。

### 4. 衍生欄位：存可以算出來的值

例如存「總金額」，而不是每次都用 單價 × 數量 加總。

## ⚠️ 反正規化的代價：要維持一致性

資料存了兩份，就要確保兩份**永遠一致**。常見做法：
- **Trigger**：資料變動時自動更新冗餘欄位（第 9-3 課）
- **應用程式**：在程式中同時更新
- **定期批次重算**：每天晚上重新計算一次（容許短暫不一致）
- **Materialized View**（實體化檢視表）：資料庫自動維護的「快取查詢結果」

## 💼 實務建議

1. **先正規化到 3NF**，這是預設的起點
2. 遇到**實際的效能問題**，量測確認瓶頸後，才考慮反正規化
3. 反正規化前，先試試看**加索引**、改寫查詢，通常就能解決
4. 反正規化要**寫文件**說明原因，以及一致性怎麼維護

> 「過早的最佳化是萬惡之源」——不要一開始就為了「可能的」效能問題而反正規化。
