# 5-4 安全軟體開發：SSDLC 與程式漏洞 🎯💼

> 對應考古題：111（SSDLC 開發階段 5 項、測試階段 2 項、部署與維運階段 3 項控制措施，20 分）、112（C 程式使用 `gets` 的安全性威脅、運作原理與修訂作法，15 分）

## 觀念

傳統開發是「先做出來，上線前再找資安廠商掃一掃」，發現問題時已經很難改，修正成本很高。
**安全系統發展生命週期（SSDLC，Secure System Development Life Cycle）**：在系統發展的**每個階段**都納入資安，從需求開始就把安全當成功能的一部分。

💡 越早發現問題，修正成本越低：需求階段改一行文件，上線後可能要改整個架構。

## 🎯 SSDLC 各階段的控制措施（111 年題）

111 年題目寫的是「依據 Web 應用程式安全參考指引」，題目要求的項數（開發 5、測試 2、部署與維運 3）和《**資通系統防護基準**》中「系統與服務獲得」構面的控制措施**完全吻合**。以下依國家資通安全會報技術服務中心《資通系統防護基準驗證實務》（111 年 9 月）整理：

| 階段 | 控制措施 |
|---|---|
| **需求階段** | ① 針對系統安全需求（含機密性、可用性、完整性）進行確認 |
| **設計階段** | ① 根據系統功能與要求，識別可能影響系統之威脅，進行風險分析及評估 ② 將風險評估結果回饋需求階段之檢核項目，並提出安全需求修正 |
| **開發階段**（5 項） | ① 應針對安全需求實作必要控制措施 ② 應注意避免軟體常見漏洞及實作必要控制措施 ③ 發生錯誤時，使用者頁面僅顯示簡短錯誤訊息及代碼，不包含詳細之錯誤訊息 ④ 執行「**源碼掃描**」安全檢測 ⑤ 系統應具備發生嚴重錯誤時之**通知機制** |
| **測試階段**（2 項） | ① 執行「**弱點掃描**」安全檢測 ② 執行「**滲透測試**」安全檢測 |
| **部署與維運階段**（3 項） | ① 於部署環境中應針對相關資通安全威脅，進行更新與修補，並**關閉不必要服務及埠口** ② 資通系統**不使用預設密碼** ③ 於系統發展生命週期之維運階段，應執行**版本控制與變更管理** |
| **委外階段** | 資通系統開發如委外辦理，應將系統發展生命週期各階段依等級將安全需求（含機密性、可用性、完整性）納入委外契約 |

另外還有「開發、測試及正式作業環境應為區隔」和「應儲存與管理系統發展生命週期之相關文件」兩項。

⚠️ 防護基準依系統的防護需求等級（普、中、高）規定要做哪些項目，例如「源碼掃描」只要求**高**等級系統。
⚠️ 《資通安全管理法》114 年 12 月 1 日施行新法，相關子法可能隨之修訂，考前確認最新版本。

### 各控制措施的白話說明

| 控制措施 | 為什麼要做 |
|---|---|
| 避免軟體常見漏洞 | 參考 OWASP Top 10、CWE Top 25，避免 SQL Injection、XSS 等（5-3 課） |
| 錯誤訊息不顯示細節 | 詳細的錯誤訊息（例如資料庫錯誤、程式路徑）會變成攻擊者的線索 |
| **源碼掃描**（靜態分析，SAST） | 用工具**掃描原始碼**，找出不安全的寫法；不用執行程式 |
| 嚴重錯誤通知機制 | 系統出問題時主動通知管理者（Email、簡訊），不要等使用者抱怨才發現 |
| **弱點掃描** | 用工具**掃描執行中的系統**，比對已知漏洞（例如未修補的版本、設定錯誤） |
| **滲透測試** | 由資安專家**模擬攻擊者**實際嘗試入侵，能找出工具找不到的邏輯漏洞 |
| 關閉不必要的服務和埠口 | 開越多服務，被攻擊的入口越多（縮小攻擊面） |
| 不使用預設密碼 | 設備和軟體的預設帳密在網路上都查得到，是最常被利用的弱點之一 |
| 版本控制與變更管理 | 每次修改都有紀錄、經過審核，出問題可以追查和還原（3-4 課 Git） |

### 弱點掃描 vs 滲透測試

| | 弱點掃描 | 滲透測試 |
|---|---|---|
| 方式 | **自動化工具** | **人工**為主，資安專家模擬攻擊 |
| 深度 | 廣但淺，找出「可能」的漏洞 | 深入驗證漏洞「**能不能真的被利用**」 |
| 頻率 | 可以經常做（例如每季） | 成本高，通常每年或重大改版時做 |
| 誤判 | 可能有誤報 | 較少誤報 |

## 🎯 緩衝區溢位（112 年題）

### 題目的程式

```c
char username[16];
char password[16];
...
gets(username);
gets(password);
if (strcmp(username, "testuser") == 0 && strcmp(password, "testpwd ") == 0) { ... }
```

### (一) 安全性威脅：緩衝區溢位（Buffer Overflow）

`gets()` 讀取輸入時**不檢查長度**，陣列只有 16 個位元組，使用者卻可以輸入任意長度的字串。

### (二) 危害與運作原理

```
記憶體中的堆疊（Stack），由低位址往高位址：

  [ username 16 bytes ][ 其他區域變數 ][ 舊的框架指標 ][ 返回位址 ]
          ▲
          │ 輸入 100 個字元
          └────────────────────────────────────────────▶ 超出 16 bytes 的部分
                                              一路覆蓋到後面的資料，包括返回位址
```

1. 輸入超過陣列大小時，多出來的資料會**覆蓋相鄰的記憶體**
2. 可能覆蓋其他變數，**改變程式邏輯**（例如把驗證結果改成「通過」）
3. 可能覆蓋函式的**返回位址**，函式結束時跳到攻擊者指定的位置，**執行攻擊者的程式碼**，取得系統控制權
4. 最輕微也會讓程式**當機**（破壞可用性）

這就是題目說的「可讓使用者執行不被允許的指令」。

### (三) 修訂作法

| 作法 | 說明 |
|---|---|
| **① 改用會檢查長度的函式** | `gets` 已經從 C11 標準中移除，改用 `fgets(buf, sizeof buf, stdin)`，最多只讀 `緩衝區大小 − 1` 個字元 |
| ② 驗證輸入長度與格式 | 超過長度就拒絕，不要只是截斷了事 |
| ③ 不要把帳號密碼寫死在程式中 | 題目把 `"testuser"`、`"testpwd "` 直接寫在程式碼裡，任何拿到執行檔的人都能找到。密碼應該**雜湊後**存在資料庫（4-4 課） |
| ④ 編譯器與作業系統的保護機制 | **堆疊保護**（Stack Canary，在返回位址前放一個檢查值）、**ASLR**（位址空間隨機化，讓攻擊者猜不到位址）、**DEP／NX**（資料區不能執行程式碼） |
| ⑤ 源碼掃描 | 工具會直接標出 `gets`、`strcpy`、`sprintf` 等不安全的函式 |
| ⑥ 改用記憶體安全的語言 | Java、C#、Python、Rust 等語言會自動檢查陣列邊界 |

修正後的程式（只用 C 標準函式庫）：

```c
#include <stdio.h>
#include <string.h>

/* 安全地讀取一行：最多讀 size - 1 個字元，並去掉結尾的換行 */
int read_line(char *buf, size_t size) {
    if (fgets(buf, (int)size, stdin) == NULL) {   /* 讀取失敗或沒有輸入 */
        return 0;
    }
    size_t len = strcspn(buf, "\n");              /* 找到換行字元的位置 */
    if (buf[len] == '\n') {
        buf[len] = '\0';                          /* 去掉換行 */
    } else {
        int ch;                                   /* 輸入太長：丟棄這一行剩下的字元 */
        while ((ch = getchar()) != '\n' && ch != EOF) { }
    }
    return 1;
}

int main(void) {
    char username[16];
    char password[16];

    printf("Enter your username: ");
    if (!read_line(username, sizeof username)) return 1;
    printf("Enter your password: ");
    if (!read_line(password, sizeof password)) return 1;

    /* 實務上應該查詢資料庫，比對密碼的雜湊值，不要把帳密寫死在程式中 */
    if (strcmp(username, "testuser") == 0 && strcmp(password, "testpwd") == 0) {
        printf("Access granted!\n");
    } else {
        printf("Access denied!\n");
    }
    return 0;
}
```

💡 原題的比較字串是 `"testpwd "`（結尾多一個空白），而且 `= =` 中間有空格會編譯錯誤，可能是排版問題。作答時以題目要問的**安全性**為主，可以順帶指出。

### 常見的不安全 C 函式

| 不安全 | 安全的替代 |
|---|---|
| `gets` | `fgets` |
| `strcpy` | `strncpy`、`strlcpy`（或先檢查長度） |
| `strcat` | `strncat` |
| `sprintf` | `snprintf` |
| `scanf("%s", buf)` | `scanf("%15s", buf)`（指定最大寬度） |

## 💼 工作實作

### 委外開發的資安要求

國營事業的系統多半委外開發，你很可能是**承辦人**，要負責：
1. **需求書（RFP）寫進資安需求**：依系統等級列出防護基準的控制措施，技服中心有「資通系統委外開發 RFP 資安需求範本」可以參考
2. **合約約定責任**：要求廠商提供源碼掃描、弱點掃描報告，修補發現的漏洞，以及保密和事件通報義務
3. **驗收時檢查**：確認高風險漏洞都已修補、預設帳密已移除、正式環境和測試環境分開
4. **上線後維運**：定期更新修補、版本控制、變更要經過審核

### 開發時的好習慣

- 錯誤頁面只顯示「系統發生錯誤，代碼 E1023，請聯絡管理員」，詳細錯誤寫在伺服器的日誌裡
- 程式碼送出前跑一次靜態分析工具（例如 SonarQube 或 IDE 內建的檢查）
- 不要把密碼、API 金鑰寫在程式碼或上傳到 Git

## 📝 考古題示範

### 111 年：依 Web 應用程式安全參考指引，列出 SSDLC 開發階段 5 項、測試階段 2 項、部署與維運階段 3 項控制措施

> 參考答案（依《資通系統防護基準》整理，不是官方公布的答案）

**（一）開發階段（5 項）**
1. 針對安全需求實作必要控制措施
2. 注意避免軟體常見漏洞（如 OWASP Top 10）並實作必要控制措施
3. 發生錯誤時，使用者頁面僅顯示簡短錯誤訊息及代碼，不包含詳細錯誤訊息
4. 執行「源碼掃描」安全檢測
5. 系統應具備發生嚴重錯誤時之通知機制

**（二）測試階段（2 項）**
1. 執行「弱點掃描」安全檢測
2. 執行「滲透測試」安全檢測

**（三）部署與維運階段（3 項）**
1. 於部署環境中針對資通安全威脅進行更新與修補，並關閉不必要的服務及埠口
2. 資通系統不使用預設密碼
3. 維運階段執行版本控制與變更管理
