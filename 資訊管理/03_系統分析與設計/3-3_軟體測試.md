# 3-3 軟體測試 🎯💼

> 對應考古題：105（依使用手冊，替「輸入三角形三邊正整數，判斷為何種三角形」的軟體設計完整測試個案）、108（請說明何謂單元測試）

## 觀念

**軟體測試**：執行程式，找出**錯誤**，確認系統**符合需求**。

| 名詞 | 意思 |
|---|---|
| **驗證**（Verification） | 「**有沒有把東西做對**」：是否符合規格 |
| **確認**（Validation） | 「**有沒有做對的東西**」：是否符合使用者真正的需求 |

⚠️ 測試只能證明錯誤**存在**，不能證明錯誤**不存在**。

## 🎯 測試層級

```
  需求 ◀────────────── 驗收測試（使用者確認符合需求）
   系統設計 ◀──────── 系統測試（整個系統的功能、效能、安全）
     模組設計 ◀────── 整合測試（模組之間的介面）
       程式碼 ◀────── 單元測試（單一函式或模組）
```
（左邊是開發階段，右邊是對應的測試，這個對應關係稱為 **V 模型**。）

| 層級 | 測什麼 | 誰測 | 例子 |
|---|---|---|---|
| **單元測試**（Unit Test） | **最小單位**：單一函式、方法或模組，**獨立**測試 | 開發人員 | 測試「計算電費」函式，輸入不同度數看結果對不對 |
| **整合測試**（Integration Test） | 模組**組合起來**後，彼此的**介面**和資料傳遞 | 開發人員、測試人員 | 訂單模組呼叫庫存模組，資料是否正確傳遞 |
| **系統測試**（System Test） | **整個系統**是否符合規格，包括**非功能需求** | 測試團隊 | 功能、效能（壓力測試）、安全（弱點掃描）、相容性 |
| **驗收測試**（Acceptance Test） | 由**使用者**確認系統符合需求，決定是否接受 | **使用者**、業主 | 使用者驗收測試（UAT） |

驗收測試的兩種：
- **Alpha 測試**：在開發環境，由使用者或內部人員測試
- **Beta 測試**：在真實環境，由部分真實使用者試用

### 整合測試的方式

| 方式 | 說明 |
|---|---|
| **由上而下** | 先測上層模組，下層還沒寫好的用**樁程式（Stub）**代替 |
| **由下而上** | 先測下層模組，上層用**驅動程式（Driver）**呼叫 |
| **大爆炸** | 全部模組一次組合測試，出錯時很難找原因 |

### 回歸測試（Regression Test）

**修改程式後，重新執行之前的測試**，確認修改沒有弄壞原本正常的功能。通常用自動化測試（3-4 課 CI）。

## 🎯 黑箱測試與白箱測試

| | 黑箱測試（Black-box） | 白箱測試（White-box） |
|---|---|---|
| 依據 | **規格**（輸入和預期輸出），**不看程式碼** | **程式碼的內部邏輯** |
| 別名 | 功能測試 | 結構測試、玻璃箱測試 |
| 找出 | 功能遺漏、規格不符、介面錯誤 | 邏輯錯誤、沒執行到的程式碼 |
| 誰做 | 測試人員、使用者 | 開發人員 |

### 🎯 黑箱測試技術

| 技術 | 做法 | 例子：年齡欄位，有效範圍 18～65 |
|---|---|---|
| **等價分割**（Equivalence Partitioning） | 把輸入分成幾個**行為相同的群組**，每組挑一個代表值 | 無效（<18）：10；有效（18～65）：30；無效（>65）：70 |
| **邊界值分析**（Boundary Value Analysis） | 錯誤常發生在**邊界**，測邊界和邊界旁邊的值 | 17、**18**、19、64、**65**、66 |
| **決策表**（Decision Table） | 列出條件的所有組合和對應動作 | 「會員 × 滿千元」四種組合的折扣 |

### 白箱測試的涵蓋率

| 涵蓋率 | 要求 | 強度 |
|---|---|---|
| **敘述涵蓋**（Statement Coverage） | 每一行程式**至少執行一次** | 最弱 |
| **分支涵蓋**（Branch Coverage） | 每個判斷的 **True 和 False** 都至少走過一次 | 較強 |
| **路徑涵蓋**（Path Coverage） | **所有可能的執行路徑**都走過 | 最強，但路徑可能太多 |

## 🎯 測試個案（Test Case）

一個測試個案通常包含：

| 欄位 | 說明 |
|---|---|
| 編號 | TC-01 |
| **測試目標** | 這個個案要驗證什麼 |
| 前置條件 | 執行前的狀態（例如已登入） |
| **測試程序**（步驟與輸入資料） | 怎麼操作、輸入什麼 |
| **測試準則**（預期結果） | 應該得到什麼結果才算通過 |
| 實際結果、是否通過 | 執行後填寫 |

## 💼 工作實作

- **驗收測試是承辦人的責任**：委外系統上線前，承辦人要安排業務單位做 **UAT**，依需求規格逐項設計測試個案，測試通過才簽驗收。不要只看廠商的展示就驗收
- **用真實情境設計測試**：除了正常流程，一定要測**錯誤輸入**和**邊界**（空白、超長、負數、特殊符號）。很多資安漏洞（5-3 課）就是因為沒測錯誤輸入
- **測試資料不要用真實個資**：測試環境要用假資料或去識別化的資料（5-4 課環境區隔）
- **單元測試工具**：Java 用 JUnit、Python 用 pytest、JavaScript 用 Jest。寫好的單元測試可以在每次修改後自動執行（3-4 課 CI）

## 📝 考古題示範

### 108 年：請說明何謂單元測試（Unit Test）

> 參考答案（自己寫的，不是官方答案）

單元測試是針對程式中**最小可測試單位**（如單一函式、方法或模組）所進行的測試，在與其他模組隔離的情況下，驗證其在各種輸入下是否產生正確的輸出。通常由開發人員在開發階段撰寫並執行，常以 JUnit、pytest 等框架自動化。其優點是能及早發現錯誤、降低除錯成本，並作為日後修改程式時的回歸測試基礎。

### 105 年：替三角形判斷軟體設計完整測試個案

> 題目：軟體依輸入的三角形三邊**正整數**，判斷並輸出三角形種類（正三角形、直角三角形、等腰三角形、等腰直角三角形、一般三角形），請設計完整的測試個案（含測試目標、測試程序、測試準則）。
> 參考答案（自己寫的，不是官方答案）

**設計思路**：用**等價分割**涵蓋每一種輸出，用**邊界值**測試「剛好不能構成三角形」的情況，再加上**無效輸入**。

| 編號 | 測試目標 | 測試程序（輸入三邊） | 測試準則（預期結果） |
|---|---|---|---|
| TC-01 | 正三角形 | 5, 5, 5 | 輸出「正三角形」 |
| TC-02 | 等腰三角形 | 5, 5, 3 | 輸出「等腰三角形」 |
| TC-03 | 等腰三角形（相等的邊在不同位置） | 5, 3, 5 和 3, 5, 5 | 都輸出「等腰三角形」 |
| TC-04 | 直角三角形 | 3, 4, 5 | 輸出「直角三角形」 |
| TC-05 | 直角三角形（斜邊在不同位置） | 5, 3, 4 和 4, 5, 3 | 都輸出「直角三角形」 |
| TC-06 | 一般三角形 | 4, 5, 6 | 輸出「一般三角形」 |
| TC-07 | 等腰直角三角形 | 見下方說明 | 確認處理方式符合規格 |
| TC-08 | 邊界：兩邊和**等於**第三邊（不能構成三角形） | 1, 2, 3 | 輸出「無法構成三角形」 |
| TC-09 | 兩邊和**小於**第三邊 | 1, 2, 5 | 輸出「無法構成三角形」 |
| TC-10 | 邊界：兩邊和**剛好大於**第三邊 | 2, 3, 4 | 輸出「一般三角形」 |
| TC-11 | 無效輸入：0 | 0, 4, 5 | 輸出錯誤訊息 |
| TC-12 | 無效輸入：負數 | −3, 4, 5 | 輸出錯誤訊息 |
| TC-13 | 無效輸入：非整數 | 3.5, 4, 5 | 輸出錯誤訊息（規格要求正整數） |
| TC-14 | 無效輸入：非數字 | a, 4, 5 | 輸出錯誤訊息 |
| TC-15 | 無效輸入：個數不對 | 3, 4 | 輸出錯誤訊息 |
| TC-16 | 極大值 | 2147483647, 2147483647, 2147483647 | 輸出「正三角形」，不因溢位而出錯 |

**TC-07 的說明**：等腰直角三角形的三邊比例是 1 : 1 : √2，**斜邊不可能是整數**，所以「三邊都是正整數」時，這種三角形**不會出現**。測試時應該：
1. 確認規格的意圖（例如是否接受小數，或這個選項是否多餘）
2. 確認程式不會把接近的整數（例如 5, 5, 7）誤判為等腰直角三角形，應輸出「等腰三角形」

💡 指出規格中的矛盾或遺漏，本身就是測試人員的重要工作，答題時寫出來會加分。
