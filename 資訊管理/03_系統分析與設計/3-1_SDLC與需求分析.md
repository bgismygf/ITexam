# 3-1 系統發展生命週期與需求分析 🎯💼

> 屬於官方命題大綱「二、系統分析與設計」。105～115 年沒有單獨考過，但它是 3-2～3-5 課（UML、測試、Git、專案管理）的基礎，也和 5-4 課的 SSDLC 對應。

## 🎯 系統發展生命週期（SDLC）

**SDLC（System Development Life Cycle）**：開發一個資訊系統，從構想到汰換的完整過程。

| 階段 | 做什麼 | 產出 |
|---|---|---|
| **① 規劃**（Planning） | 確認問題和目標、評估**可行性**、訂定專案範圍和時程 | 可行性分析報告、專案計畫 |
| **② 分析**（Analysis） | 了解現行作業、蒐集和確認**使用者需求**（系統要做**什麼**） | 需求規格書、DFD、使用案例圖 |
| **③ 設計**（Design） | 決定系統**怎麼做**：架構、資料庫、介面、程式模組 | 系統設計書、ER 圖、UML |
| **④ 實作**（Implementation） | 寫程式、建資料庫 | 程式碼 |
| **⑤ 測試**（Testing） | 驗證系統符合需求、找出錯誤（3-3 課） | 測試報告 |
| **⑥ 部署**（Deployment） | 安裝上線、資料轉換、教育訓練 | 上線系統、使用手冊 |
| **⑦ 維護**（Maintenance） | 修正錯誤、因應新需求調整 | 變更紀錄 |

💡 5-4 課的 SSDLC 就是在每個階段加入資安控制措施。

### 🎯 可行性分析

| 面向 | 問的問題 |
|---|---|
| **技術**可行性 | 現有技術、人力做得出來嗎？ |
| **經濟**可行性 | 效益大於成本嗎？（成本效益分析） |
| **作業**可行性 | 使用者會接受、會用嗎？符合組織的作業方式嗎？ |
| **時程**可行性 | 能在期限內完成嗎？ |
| **法律**可行性 | 符合法規（例如個資法）嗎？ |

### 系統維護的四種類型

| 類型 | 說明 | 例子 |
|---|---|---|
| **修正性**（Corrective） | 修正錯誤 | 報表金額算錯 |
| **調適性**（Adaptive） | 因應環境改變 | 作業系統升級、法規修改 |
| **完善性**（Perfective） | 增加功能或改善效能 | 使用者要求新報表 |
| **預防性**（Preventive） | 預防未來的問題 | 重構難以維護的程式 |

## 🎯 開發模式

| 模式 | 做法 | 優點 | 缺點 | 適合 |
|---|---|---|---|---|
| **瀑布式**（Waterfall） | 依序完成每個階段，**前一階段完成才進入下一階段**，像瀑布一樣不回頭 | 階段清楚、文件完整、容易管理 | 需求變更困難；**很晚才看到成品**，問題發現得晚 | 需求明確、穩定的系統 |
| **雛形法**（Prototyping） | 先快速做出**簡易雛形**給使用者試用，依回饋修改 | 使用者早期參與，需求更明確 | 使用者可能把雛形當成品；文件可能不完整 | 需求不明確 |
| **螺旋式**（Spiral） | 反覆循環「規劃 → **風險分析** → 開發 → 評估」，每一圈擴大 | 重視**風險管理** | 複雜，需要風險評估專業 | 大型、高風險專案 |
| **漸增式／反覆式**（Incremental／Iterative） | 把系統分成幾個部分，**分批**開發和交付 | 早點交付可用的功能 | 需要良好的整體架構規劃 | 中大型系統 |
| **敏捷式**（Agile） | **短週期**反覆開發，持續交付可運作的軟體，擁抱變更 | 回應變化快，使用者持續參與 | 文件較少；需要使用者高度投入 | 需求常變動的專案 |

### 🎯 敏捷宣言的四個價值

| 更重視 | 勝過 |
|---|---|
| **個人與互動** | 流程與工具 |
| **可用的軟體** | 詳盡的文件 |
| **與客戶合作** | 合約協商 |
| **回應變化** | 遵循計畫 |

（右邊的項目也有價值，只是左邊的更重要。）

### 🎯 Scrum（最常見的敏捷框架）

| 類別 | 內容 |
|---|---|
| **角色** | **產品負責人**（Product Owner）：決定做什麼、排優先順序；**Scrum Master**：排除障礙、確保團隊遵循 Scrum；**開發團隊**：自組織完成工作 |
| **產出物** | **產品待辦清單**（Product Backlog）：所有想做的功能；**衝刺待辦清單**（Sprint Backlog）：這次衝刺要做的；**增量**（Increment）：每次衝刺完成、可運作的成果 |
| **活動** | **衝刺**（Sprint，通常 1～4 週）；衝刺規劃會議；**每日站立會議**（Daily Scrum，15 分鐘）；衝刺審查會議（展示成果）；衝刺回顧會議（檢討改進） |

### DevOps

**DevOps**：結合開發（Development）和維運（Operations），透過自動化（3-4 課的 CI/CD）和協作，讓軟體能**頻繁、可靠**地交付和上線。

## 🎯 需求分析

### 功能需求與非功能需求

| 種類 | 意思 | 例子 |
|---|---|---|
| **功能需求** | 系統**要做什麼** | 使用者可以線上申請停電通知、系統每月產生用電報表 |
| **非功能需求** | 系統要**做得多好**（品質限制） | **效能**：查詢 3 秒內回應；**可用性**：全年 99.9% 可用；**安全性**：要多因子認證；**易用性**、可維護性、相容性 |

⚠️ 資安需求屬於非功能需求，要在需求階段就寫清楚（5-4 課 SSDLC 需求階段）。

### 需求蒐集方法

| 方法 | 說明 | 適合 |
|---|---|---|
| **訪談** | 和使用者一對一或小組深入討論 | 了解細節和例外狀況 |
| **問卷** | 大量發放蒐集意見 | 使用者多、分散各地 |
| **觀察** | 實際觀看使用者怎麼工作 | 使用者說不清楚的隱性流程 |
| **文件分析** | 研讀現有表單、報表、作業手冊、法規 | 了解現行作業 |
| **聯合應用設計**（JAD） | 使用者、主管、開發人員一起開密集的工作會議 | 快速取得共識 |
| **雛形** | 做出畫面讓使用者試用 | 需求不明確時 |

## 🎯 結構化分析：資料流程圖（DFD）

**DFD（Data Flow Diagram）**：描述資料在系統中**如何流動、被如何處理**，只看資料，不看控制流程和時間順序。

### 四個符號

| 元件 | 意思 | 常見符號 |
|---|---|---|
| **外部實體**（External Entity） | 系統外部、提供或接收資料的人或系統 | 方框 ▭ |
| **處理**（Process） | 把輸入資料轉換成輸出資料 | 圓形 ○ 或圓角矩形 |
| **資料儲存**（Data Store） | 存放資料的地方 | 開口矩形 ═ |
| **資料流**（Data Flow） | 資料的移動方向 | 箭頭 → |

### 例：線上申請停電通知

```
                  申請資料                      申請紀錄
  ┌────────┐  ─────────────▶  ( 1.0 受理申請 ) ─────────▶ ═ D1 申請檔 ═
  │ 用戶    │                         │
  └────────┘  ◀─────────────          │ 停電區域
       ▲         受理通知              ▼
       │                      ( 2.0 比對停電區域 ) ◀───── ═ D2 停電計畫檔 ═
       │          停電通知             │
       └──────────────────────────────┘
```

### DFD 的分層

| 層級 | 說明 |
|---|---|
| **系統環境圖**（Context Diagram，第 0 層的上一層） | 整個系統畫成**一個處理**，只顯示和外部實體之間的資料流 |
| **第 0 層圖**（Level 0） | 把系統拆成幾個主要處理 |
| **第 1、2…層** | 再把每個處理往下拆細 |

⚠️ 層級的編號各教科書不同，有些把系統環境圖稱為第 0 層，第 0 層圖改稱第 1 層。作答時寫清楚「系統環境圖」和「下一層的分解圖」即可。

**平衡原則**：上下層的輸入和輸出資料流要一致。

### DFD 常見錯誤

- 資料**不能**直接從外部實體流到資料儲存，或從資料儲存流到資料儲存，中間一定要經過**處理**
- 處理一定要有輸入和輸出（只有輸入叫「黑洞」，只有輸出叫「奇蹟」）

## 💼 工作實作

國營事業的系統多半**委外開發**，你很可能是**業務承辦人**或**資訊承辦人**，負責：

| 階段 | 承辦人要做的事 |
|---|---|
| 規劃 | 簽辦採購、編列預算、評估可行性 |
| 分析 | 撰寫**需求規格**放進招標文件（RFP）；需求寫不清楚，驗收時就會吵架 |
| 設計 | 審查廠商的設計文件 |
| 測試 | 安排使用者驗收測試（UAT，3-3 課） |
| 部署 | 安排教育訓練、資料轉換、上線公告 |
| 維護 | 管理保固和維護合約、處理變更需求 |

寫需求的好習慣：每條需求要**明確、可驗證**。「系統要很快」不能驗收，「查詢結果在 3 秒內顯示」才可以。
