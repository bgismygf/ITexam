# 3-2 系統設計：模組化與 UML 🎯💼

> 對應考古題：106（請解釋何為耦合力）、113（列舉 4 種 UML 常用圖表並分別繪圖說明，16 分）

## 🎯 模組化設計

**模組化**：把大系統拆成多個功能獨立的小**模組**，每個模組負責一件事。好處是容易開發、測試、維護和重複使用。

評估模組品質的兩個指標：

| 指標 | 意思 | 好的設計 |
|---|---|---|
| **內聚力**（Cohesion） | 一個模組**內部**各元素之間關係的緊密程度 | **高內聚**：模組只做一件事，裡面的東西都為這件事服務 |
| **耦合力**（Coupling） | 模組**之間**互相依賴的程度 | **低耦合**：修改一個模組，不會牽動其他模組 |

💡 **記法**：好設計是「**高內聚、低耦合**」，就像好的部門分工：部門內團結專注，部門間介面清楚、不互相干涉。

### 🎯 耦合力的種類（由好到差）

| 種類 | 說明 | 例子 |
|---|---|---|
| **資料耦合**（Data） | 模組之間只透過**參數傳遞必要的資料** | `計算稅額(金額)` |
| **標記耦合**（Stamp） | 傳遞**整個資料結構**，但只用到其中一部分 | 傳整筆員工資料，只用到薪資 |
| **控制耦合**（Control） | 傳遞**控制旗標**，決定另一個模組的執行流程 | `列印(資料, 模式旗標)`，旗標決定印哪種格式 |
| **外部耦合**（External） | 共同依賴外部的格式、裝置或協定 | 都依賴同一個外部檔案格式 |
| **共用耦合**（Common） | 共用**全域變數** | 多個模組修改同一個全域變數，出錯很難追 |
| **內容耦合**（Content） | 一個模組**直接修改或跳進**另一個模組的內部 | 直接修改另一個模組的區域變數 |

### 內聚力的種類（由好到差）

| 種類 | 說明 |
|---|---|
| **功能內聚**（Functional） | 所有元素共同完成**單一功能**（最好） |
| **循序內聚**（Sequential） | 前一個元素的輸出是下一個的輸入 |
| **通訊內聚**（Communicational） | 處理**同一份資料** |
| **程序內聚**（Procedural） | 依特定順序執行，但處理不同資料 |
| **時間內聚**（Temporal） | 在**同一時間**執行（例如系統初始化時要做的所有事） |
| **邏輯內聚**（Logical） | 邏輯上同一類，用參數選擇做哪一個 |
| **偶然內聚**（Coincidental） | 元素之間**沒有關係**，只是剛好放在一起（最差） |

## 🎯 UML（統一塑模語言）

**UML（Unified Modeling Language）**：用來**視覺化、設計和記錄**軟體系統的標準圖形語言，由 OMG 組織維護。UML 2.x 共有 14 種圖，分成兩大類：

| 類別 | 描述什麼 | 常用的圖 |
|---|---|---|
| **結構圖**（靜態） | 系統**由什麼組成** | **類別圖**、物件圖、元件圖、部署圖、套件圖 |
| **行為圖**（動態） | 系統**怎麼運作** | **使用案例圖**、**活動圖**、**循序圖**、**狀態圖**、通訊圖 |

考試最常考的是下面五種。以「**網路書店**」為例：

### ① 使用案例圖（Use Case Diagram）— 系統**有哪些功能、誰會用**

用在**需求分析**階段，從使用者的角度描述系統功能。

```
                 ┌───────────── 網路書店系統 ─────────────┐
                 │                                        │
    O            │      ( 瀏覽書籍 )                       │
   /|\ ──────────┼───── ( 下訂單 ) ─ ─ <<include>> ─ ─▶ ( 登入 )
   / \           │           │                            │
   會員           │           └─ ─ <<extend>> ─ ─ ( 使用折價券 )
                 │                                        │
    O            │                                        │
   /|\ ──────────┼───── ( 管理書籍資料 )                    │
   / \           │                                        │
  管理員          └────────────────────────────────────────┘
```

| 符號 | 意思 |
|---|---|
| 人形 | **參與者**（Actor）：使用系統的人或外部系統 |
| 橢圓 | **使用案例**：系統提供的一項功能 |
| 方框 | **系統邊界** |
| `<<include>>` | **一定會**包含（下訂單一定要先登入） |
| `<<extend>>` | **有條件時**才延伸（有折價券才使用） |

### ② 類別圖（Class Diagram）— 系統**有哪些類別、彼此的關係**

用在**設計**階段，是物件導向設計最核心的圖，也可以對應到資料表。

```
  ┌──────────────────┐            ┌──────────────────┐
  │     會員          │ 1      0..*│     訂單          │
  ├──────────────────┤────────────├──────────────────┤
  │ - 會員編號：String │   下訂      │ - 訂單編號：String │
  │ - 姓名：String     │            │ - 訂購日期：Date   │
  ├──────────────────┤            ├──────────────────┤
  │ + 登入()          │            │ + 計算總額()       │
  └────────△─────────┘            └────────◆─────────┘
           │ 繼承                            │ 組合 1..*
  ┌────────┴─────────┐            ┌────────┴─────────┐
  │    VIP 會員       │            │    訂單明細        │
  ├──────────────────┤            ├──────────────────┤
  │ - 折扣率：double   │            │ - 數量：int        │
  └──────────────────┘            └──────────────────┘
```

| 符號 | 意思 |
|---|---|
| 三格方框 | 類別名稱 / **屬性** / **方法**；`-` 私有、`+` 公開、`#` 保護 |
| 實線 | **關聯**（Association），兩端標**多重性**（1、0..*、1..*） |
| 空心三角形 △ | **繼承**（Generalization）：VIP 會員是一種會員 |
| 空心菱形 ◇ | **聚合**（Aggregation）：整體和部分可以獨立存在（系所和老師） |
| 實心菱形 ◆ | **組合**（Composition）：部分**不能**脫離整體存在（訂單刪除，明細也消失） |
| 虛線箭頭 | **相依**（Dependency） |

### ③ 循序圖（Sequence Diagram）— 物件之間**依時間順序**怎麼互動

```
   會員          網頁介面          訂單系統          庫存系統
    │               │                 │                 │
    │ 1: 送出訂單    │                 │                 │
    │──────────────▶│ 2: 建立訂單       │                 │
    │               │────────────────▶│ 3: 檢查庫存       │
    │               │                 │────────────────▶│
    │               │                 │ 4: 庫存足夠       │
    │               │                 │◀─ ─ ─ ─ ─ ─ ─ ─ │
    │               │ 5: 訂單成立       │                 │
    │ 6: 顯示成功    │◀─ ─ ─ ─ ─ ─ ─ ─ │                 │
    │◀─ ─ ─ ─ ─ ─ ─ │                 │                 │
    ▼  時間往下      ▼                 ▼                 ▼
```

| 符號 | 意思 |
|---|---|
| 上方方框＋往下的虛線 | **物件**和它的**生命線**（Lifeline） |
| 實線箭頭 | 呼叫（傳送訊息） |
| 虛線箭頭 | 回傳 |
| 由上往下 | **時間順序** |

### ④ 活動圖（Activity Diagram）— 工作**流程**

和流程圖很像，可以表示**分支**和**平行**處理，常用來描述業務流程。

```
        ●  開始
        │
   ┌────▼─────┐
   │ 選購書籍  │
   └────┬─────┘
        ◇  是否為會員？
     否 │ \ 是
   ┌────▼──┐  \────────┐
   │ 註冊   │           │
   └────┬──┘           │
        └──────┬───────┘
          ┌────▼─────┐
          │ 結帳付款  │
          └────┬─────┘
      ═════════╪═════════   ← 分岔：之後兩件事同時進行
          │          │
     ┌────▼───┐ ┌────▼───┐
     │ 寄確認信 │ │ 安排出貨 │
     └────┬───┘ └────┬───┘
      ═════════╪═════════   ← 合併：兩件事都完成才繼續
               ◉  結束
```

| 符號 | 意思 |
|---|---|
| 實心圓 ● | 開始 |
| 圓角方框 | 活動 |
| 菱形 ◇ | 決策（分支） |
| 粗橫線 ═ | 分岔／合併（平行處理） |
| 圓圈中實心圓 ◉ | 結束 |

### ⑤ 狀態圖（State Machine Diagram）— 一個物件的**狀態變化**

```
  ●──▶ [ 已成立 ] ──付款──▶ [ 已付款 ] ──出貨──▶ [ 已出貨 ] ──簽收──▶ [ 已完成 ] ──▶ ◉
           │
           └──取消──▶ [ 已取消 ] ──▶ ◉
```

方框是**狀態**，箭頭上標**觸發轉換的事件**。

### 各圖的用途比較

| 圖 | 回答的問題 | 用在哪個階段 |
|---|---|---|
| 使用案例圖 | 系統**有哪些功能**？誰會用？ | 需求分析 |
| 類別圖 | 系統**由哪些類別組成**？關係是什麼？ | 設計 |
| 循序圖 | 物件之間**依什麼順序**互動？ | 設計 |
| 活動圖 | **流程**怎麼走？ | 分析、設計 |
| 狀態圖 | 一個物件**有哪些狀態**、怎麼轉換？ | 設計 |

## 💼 工作實作

- **畫圖工具**：draw.io（免費、可離線）、PlantUML（用文字寫出圖，可以放進 Git 版本控制）、Visio
- **審查廠商的設計文件**：委外系統的設計書常附使用案例圖和類別圖。看得懂這些圖，才能判斷廠商有沒有漏掉需求
- **和使用者溝通**用使用案例圖和活動圖（容易看懂），**和開發人員溝通**用類別圖和循序圖
- **低耦合的實務**：系統之間用 **API** 交換資料（資料耦合），不要直接存取對方的資料庫（接近內容耦合），否則對方一改資料表，你的系統就壞了

## 📝 考古題示範

### 106 年：請解釋何為耦合力（Coupling）

> 參考答案（自己寫的，不是官方答案）

耦合力是指系統中**模組之間相互依賴的程度**。耦合力越低，模組越獨立，修改一個模組時越不會影響其他模組，系統越容易維護、測試與重複使用。良好的系統設計應追求「低耦合、高內聚」。

耦合力由低（好）到高（差）可分為：資料耦合、標記耦合、控制耦合、外部耦合、共用耦合、內容耦合。設計時應盡量只透過參數傳遞必要資料（資料耦合），避免共用全域變數或直接修改其他模組的內部資料。

### 113 年：請列舉 4 種 UML 常用圖表並分別繪圖說明（16 分）

> 參考答案（自己寫的，不是官方答案）

UML 是用於系統分析與設計的標準塑模語言，分為描述靜態結構的結構圖與描述動態行為的行為圖。常用的 4 種如下（每種都要**畫圖＋說明用途與符號**，以網路書店為例）：

1. **使用案例圖**：畫出參與者（會員、管理員）、系統邊界與使用案例（瀏覽書籍、下訂單、登入），說明它在需求分析階段描述系統功能與使用者
2. **類別圖**：畫出會員、訂單、訂單明細類別（含屬性、方法）、關聯與多重性、繼承、組合，說明它在設計階段描述系統的靜態結構
3. **循序圖**：畫出會員、網頁介面、訂單系統、庫存系統的生命線與依時間順序的訊息，說明它描述物件間的互動順序
4. **活動圖**：畫出從選購、判斷是否會員、結帳，到平行寄信與出貨的流程，說明它描述業務流程與平行處理

（圖請參考上方各圖。16 分的題目，每種圖約 4 分，**圖和說明都要有**。）
